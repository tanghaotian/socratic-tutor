# Agent 化收益与风险评估

> 版本：1.0 · 评估日期：2026-09-13 · 评估对象：socratic-tutor v0.7.0（工作区实测：`tsc --noEmit` EXIT=0；git `master` 0 commit，15 项 untracked）
> 结论口径：**支持"选择性 agent 化"，反对"整体 agent 化"**。详见第 7 节。

---

## 1. 术语界定：这个项目里的"agent 化"到底指什么

讨论收益与风险前必须先钉住口径，否则容易把"加个工具调用"和"把系统交给 LLM 自主编排"混为一谈。

仓库现状是**三层结构**，只有中间一层与 agent 化有关：

| 层 | 现状 | 是否受 agent 化影响 | 证据 |
| --- | --- | --- | --- |
| ① 能力层（业务引擎） | 教学/画像/计划/复盘/反思/skillgen/RAG **已全部实现且可被调用** | 否，基本复用 | `src/engines/**`、`src/storage/**` |
| ② 编排层（单轮流水线） | **硬编码 4 步**：解析信号 → 更新画像 → 生成动作 → 落盘录制。LLM 只在两端做"文本生成"与"JSON 抽取" | **是，这是 agent 化要替换的唯一一层** | `src/web/index.ts:110-151`、`src/mcp/tools.ts:46-67` |
| ③ 接入层（对外能力面） | Web REST 12 条路由 + MCP 7 工具，语义已与页面一致 | 否，可直接复用为 agent 的 tool 集 | `src/web/index.ts`、`src/mcp/tools.ts:144-230` |

**本项目语境下的 agent 化 = 用 LLM 驱动的多步 tool-calling loop，替换 ② 的确定性单轮编排。**

具体包含四件事：引入 tool-calling 能力 → 建会话状态 → 让模型自主选工具/决定追问步数 → 加循环与预算边界。

**重要判断**：本项目的"自我进化"机制（skill 热插拔、评测回测门禁、反思升级、锚定反思）**已经在 LLM 编排循环之外独立存在**，且比多数 agent 项目的记忆/反思机制更完整。因此 agent 化的**增量收益集中在"单轮对话决策质量"，而不是"系统终于会自我进化"**——后者是常见的高估点。

### 1.1 现状的硬事实（量化基线）

- 编排层**零 tool-calling**：`LLMProvider` 只有 `chat` / `streamChat` / `structuredCall`，全仓 `tools`/`tool_choice`/`tool_use` 在 provider 层零命中（`src/providers/interfaces.ts:4-12`）。（注：底层是 `openai` SDK，能力可用，只是未被抽象暴露。）
- 教学题型路由是**规则 switch**，LLM 只负责在给定题型下写一句话（`src/engines/skills/socratic/core.ts:42-79,93-114`）。
- **对话历史恒为空**：`history: []` 三处硬编码（`src/web/index.ts:133`、`:196`、`src/mcp/tools.ts:64`），叠加 `latestConsecutive`/`consecutiveHit` 依赖历史 → "连续 2 次 confused → hint" 在实践中**永不触发**（HANDOFF.md 第 14 条 / BUG-004）。
- 单轮交互的 LLM 调用次数：**1~2 次**（信号判定 1 次 + 文案 1 次，且有规则兜底）。这是成本评估的分母。
- 会话/多用户**未实现**：`learnerId` 硬编码 `'local-user'`（`src/web/index.ts:76`）。
- 测试 136 例、前端零构建（`public/index.html` 单文件 Vue CDN）、`tsc --noEmit` 通过。

## 2. 收益清单（按"是否真的需要 agent"排序）

### 收益 A：补上"对话"这件事本身 —— **真收益，且是当前最大短板**
现状每轮独立、无历史、题型由规则决定，**本质上不是对话式教学，是"单轮问答 + 状态累积"**。真正的多轮追问（"你上次说的 X 和刚才的 Y 矛盾在哪"）在现行架构下**结构上不可能**。
agent 化天然要求维护消息序列，**顺手把 BUG-004 这条 P0 死代码修掉**（收益 A 与 BUG-004 修复高度重叠，见第 7 节：BUG-004 应独立先修）。

### 收益 B：动态诊断路径 —— **真收益，但收益上限受产品质量目标约束**
规则路由只能表达 5 种题型（open/focus/conflict/self_eval/hint）。真实教学里"学生答错是因为概念混淆、计算失误还是读题错"需要不同处置，且**需要先追问再定性**。agent loop 可先提一个鉴别性问题，再决定给提示还是换例子。
风险对冲：苏格拉底教学法的核心约束是"不直接给答案"，agent 化后**这个约束必须由 prompt + 后置校验双重保证**，否则会退化成"通用聊天机器人"（见风险 R3）。

### 收益 C：工具组合的上下文触发 —— **真收益，中等**
现状资料检索、RAG、book-to-skill 是**用户主动点按钮**才发生。agent 化后可"讲到傅里叶变换时自动 RAG 出一段历史对话里提过的笔记，并生成一个反例"。这是把已有能力从"手动菜单"变成"按需零件"，**复用度高、增量成本低**——是性价比最好的 agent 化场景。

### 收益 D：计划/复盘的自动化编排 —— **边际收益，需谨慎**
`plan_generate` → `confirm` → 积累事件 → `review_generate` → `confirm` → 锚定反思，是一条**固定顺序的状态机**。用 agent 编排它收益有限（顺序本来就确定），但**风险显著**（自动 confirm 会绕过人工拦截）。结论：**让 agent 提议，不要让它 confirm**。

### 收益 E："思考过程可见"带来的可解释性 —— **双刃**
agent 的 trace（选了哪个工具、为什么）对教学调试有真实价值，但**不能等同于教学质量**。若把它当交付物，会催生"看起来很努力"的伪提升。

### 收益 F：与 IDE/外部 agent 的协同 —— **真收益，且已具备一半**
MCP Server（`POST /mcp`，Streamable HTTP 生命周期已对齐，7 工具，被官方 SDK 实测通过）使外部 agent（如 DSH 的 `dsh-mcp-client`，`transport: streamable-http`）**已经可以把本项目当工具集来用**。这意味着：
- **"本项目要不要 agent 化"和"本项目要不要被 agent 调用"是两个独立问题**，后者已经完成；
- 若走 agent 化，最大的收益可能不是"内建 agent 更聪明"，而是**内建 agent 与外部 agent 共享同一套 tool 契约**（`src/mcp/tools.ts` 已是现成的工具清单），避免两套逻辑漂移。

## 3. 风险清单（按严重度 × 可能性排序）

### R1（高）：破坏评测回测门禁的根基 —— **最大风险，且直击项目核心资产**
本项目最值钱的工程资产是**评测回测门禁**：冻结线程回放 + rubric LLM-as-Judge + A/B 胜率 + verdict → 人工拦截 → 应用（`src/engines/eval/**`、`src/engines/plans/eval.ts`）。

它成立的前提是**可重放的确定性**（同一快照 + 同一线程 → 可比较的输出）。agent loop 引入后：
- 同一线程每次跑的步数/工具序列不同 → baseline/candidate 的差异**混入了采样噪声**；
- A/B 胜率（如既有报告里的 3:0）在噪声下不再有统计意义；
- `SKILL_FACTORIES` 快照重建只覆盖 skill 组合，**不覆盖 agent 的策略/工具集/prompt 版本** → 快照不再完整描述"当时的系统"。

**这是"收益 vs 风险"的决定性一项**：agent 化提升的可能是对话质量，但代价可能是**失去唯一能客观判断"是否真的提升了"的机制**。
缓解（必需，非可选）：agent 的 prompt/工具集/循环上限纳入快照与版本；每线程 N 次重复取中位数；把"工具选择合理性"作为独立评分维；固定 `temperature` 与 `maxSteps`。

### R2（高）：成本与延迟的数量级变化
单轮 1~2 次 LLM 调用 → agent loop 典型 3~8 次（含工具往返与上下文重发）。**token 成本按 2~5× 估算，P95 延迟按 3~10× 估算**。对本项目有两个具体后果：
- **语音链路**：Phase 2 要求"实时可打断"，而 agent loop 的多跳延迟与"可打断"直接冲突（打断意味着要能取消在途工具调用与后续推理，现有 `runVoiceTurn` 无此抽象）；
- **本地单用户产品定位**：用户是"自己给自己用"，成本不敏感但**等待极其敏感**——教学场景里 8 秒的思考停顿会打断学习心流。行业侧的 token/延迟权衡见 [The Hidden Economics of AI Agents](https://online.stevens.edu/blog/hidden-economics-ai-agents-token-costs-latency/)。
缓解：分层——**大部分轮次走单跳**，只在检测到"需要鉴别/需要资料"时才升级到 loop；对 loop 设硬性 `maxSteps` 与 token 预算。

### R3（高）：教学法退化 —— 最不易察觉的失败
苏格拉底教学法的价值断言是"**不给答案，用提问逼出思考**"。LLM 在自由编排下的默认行为恰恰相反（被问就答、倾向给完整解释）。风险路径：
规则 switch 是**硬约束**（`buildAction` 保证一定产出提问/提示类动作）→ 换成 prompt 约束后变成**软约束**，长上下文或用户施压下会漂移。school 场景下的实测退化往往出现在"用户连续追问 3 次后，模型直接给答案"。
缓解：保留 `buildAction` 式**后置校验**（对输出的动作做类型/倾向检查，不合规则重生成或强制降级为 hint）；把"非直接给答案"（nondirect）保持为评测的**核心不可回退维**（现有 `selfbuilt.ts` 已有该维度，应继续作为一票否决）。

### R4（高）：安全边界被 agent 的"写能力"击穿
现状的写操作全在**人工拦截**之后（`confirm_upgrade`、`plan/:id/confirm`、`review/:id/confirm`、`POST /api/strategy/eval` 的 accepted 才 `applyStrategy`）。agent 化会自然产生"让 agent 自己调这些工具"的冲动，一旦放开：
- **自改代码/配置**：`summarize_resource` 会写 `knowledge/skills/<slug>.md` 并刷新 RAG；skillgen 链路可生成 skill 并应用 → **agent 可影响自己的教学策略**，这是"自主性"与"可审计性"的直接冲突；
- **间接 prompt injection**：`summarize_resource` / `searchWeb` 把**外部不可信文本**喂给模型，而模型同时握着写文件工具 —— 这是经典的间接注入 → 工具滥用的组合（参考 [NIST AI 100-2 对抗性机器学习分类](https://oecd.ai/en/dashboards/policy-initiatives/adversarial-machine-learning-a-taxonomy-and-terminology-of-attacks-and-mitigations-nist-ai-100-2e2025) 与 [OWASP LLM 应用风险（Excessive Agency）](https://safeguard.sh/resources/blog/excessive-agency-in-llm-powered-applications)）；
- 当前 `search` 是 `MockSearchProvider`，**联网一旦接真实搜索，攻击面立刻从"假数据"变成"真实网页"**。
缓解：工具**分级授权**——读类（画像/事件/RAG/检索）可直接开放；写类（落盘/确认/应用/改画像锚点）必须走 `requiresApproval` 或直接不出现在 agent 的 tool 列表里。

### R5（中高）：多步误差累积与"自信的错"
多步链路里单步错误率会被放大；教学场景的错法**特别有害**——把学生的正确理解判成错误（信号误判）会直接打击信心，比"答非所问"严重得多。现有 `SignalParser` 有规则兜底（`src/engines/signal.ts`），agent 化后若把信号判定并进自由推理，**兜底路径会消失**。
缓解：**信号判定保留为独立的、可降级的确定性/结构化调用**，不要并进 agent 的自由推理。

### R6（中）：provider 与部署兼容性被削弱
`LLMProvider` 是纯 OpenAI 兼容的 chat/json 抽象，`LLM_EXTRA_MODELS` 支持"零代码接入任意兼容模型"——这是产品的一个卖点。tool-calling 在不同兼容端点上的支持度**不一致**（部分国产兼容端点不支持并行工具调用、函数名约束、或 `tools` 字段直接报错）。agent 化会把"换模型"从"改一行 env"变成"可能不可用"。
同时：会话状态一旦落库，就会撞上既有横扩设计（`DEPLOY_MODE`、分布式锁、Web 无状态）——当前 `/mcp` 会话是**进程内内存态**，多节点下"同一会话打到另一实例"会失效。
缓解：tool-calling 作为**能力探测 + 优雅降级**（不支持则回落到现有单轮确定性路径）；会话状态外置到 SQLite 并明确一致性边界。

### R7（中）：工程与测试成本
- 现有 136 例测试对**确定性**假设很深（含 HTTP 边界 `app.inject()` 用例）；agent loop 需要 mock LLM 的脚本化多轮序列，测试会变脆。
- 提示词/工具 schema 进入版本管理后，每次调整都要重跑评测，**迭代速度变慢**。
- 项目当前 git **0 commit**（全部文件 untracked）——在这种状态下做架构级重构，**没有回滚点**，风险被额外放大（见第 7 节 P0）。

### R8（低但需登记）：收益不可证明导致的"伪 agent 化"
最现实的坏结局不是崩溃，而是：加了 loop、加了工具、看起来更高级，但**评测显示无提升甚至核心维回退**，而此时已经付出了 R1/R2/R7 的全部代价。R1 的缓解措施正是为了防止这一项变成"无法判断"。

## 4. 收益–风险对照（决策用的净额视图）

| 能力/动机 | 收益 | 主要风险 | 净判定 |
| --- | --- | --- | --- |
| 多轮真实对话（历史落库） | 高（补最大短板） | 低（与 agent 解耦） | **立即做，不需要 agent 化** |
| 动态诊断（先追问再定性） | 中高 | R3 教学法漂移、R2 延迟 | **做，限定在单跳 + 结构化决策** |
| 工具按需组合（RAG/资料/事件） | 中高 | R4 注入面、R2 成本 | **做，只开读类工具** |
| 让 agent 编排计划/复盘全流程 | 低 | R1 绕过拦截、R4 | **不做**（保持人工 confirm） |
| 让 agent 自我改写 skill/策略 | 低（已有评测门禁） | R1+R4（最严重组合） | **不做** |
| 把信号判定并进自由推理 | 0 | R5 丢掉兜底 | **不做** |
| 把 agent loop 作为默认路径 | 中 | R2 全面成本 | **不做**（应作为可选升级路径） |
| 与外部 agent 共享 tool 契约 | 中 | 低（已有 MCP） | **做，自然收敛** |

## 5. 三种方案与粗略成本

- **方案 ① 最低限度（不引入 loop）**：会话历史落库 + 传真实 history；把"题型选择"从硬编码 switch 改为**一次结构化调用**（LLM 在 5 种题型 + 是否检索中选，仍由 `buildAction` 后置校验）。成本约 **3~5 人日**（会话表 + 3 处调用点 + 测试）。**收益覆盖 A、半个 B、半个 C；风险几乎为零。**
- **方案 ② 有界 agent loop（推荐）**：在 ① 基础上引入 tool-calling，「读类工具 + maxSteps≤3 + token 预算 + 超时」硬约束；prompt/工具集/上限纳入评测快照；评测对每条线程跑 N 次取中位数；写类工具一律不进 loop。成本约 **10~15 人日**（含评测契约改造，这是大头）。
- **方案 ③ 全量 agent 化**：把编排权、写权限、自进化权全部交给模型。**不建议**——R1/R3/R4 三高项同时命中，且收益与 ② 的差距无法被现有评测证明。

共同前置（无论选哪个方案都必须先做）：
1. **git 首次提交**（当前 0 commit，无回滚点）；
2. **建立真实评测样本**（当前仅 3 条冻结线程 + 人工种子，阈值校准样本量严重不足 —— HANDOFF 第 1 条）；
3. **修 BUG-004**（独立 PR，约 1.5 人日，无契约变更，可立即验证）。

## 6. 如果推进：必须内置的护栏（Go 条件）

以下每条不满足则不应进入方案 ②：

1. **可回滚**：agent loop 由 env 开关控制（如 `AGENT_LOOP=off` 默认关闭），保留现有确定性路径为降级后端，行为与今天完全一致。
2. **可评测**：prompt 版本、工具集版本、`maxSteps`、`temperature` 全部进入快照；每线程多跑取中位数；A/B 报告标注方差与样本量。
3. **可审计**：每一步工具调用与决策写 trace（可复用 `src/tracing/` 录制层，扩成"决策轨迹"而非仅问答对）。
4. **权限最小化**：读/写工具清单分离；写类工具走审批或在 loop 中不可见；`confirm_*` 永不进 loop。
5. **教学法硬约束**：nondirect（不直接给答案）保持为一票否决的评测核心维；输出动作仍过 `buildAction` 式校验。
6. **预算硬上限**：`maxSteps`、总 token、单轮墙钟超时；超限则降级到单跳并显式标注（沿用现有 `voiceDegraded` 式的**降级可见性**传统）。
7. **provider 兼容**：tool-calling 能力探测，不支持则自动回落并告警（不能静默改变行为）。

## 7. 结论

- **收益是真实的，但主要集中在"对话能力"而非"自主进化"**：本项目已具备 skill 热插拔 + 评测门禁 + 反思/锚定闭环，agent 化**不会带来新的进化能力**，只会改变单轮对话的决策质量。把"agent 化"当作进化能力升级来立项，是**动机错配**。
- **最大的隐性代价是评测门禁的非确定性**：R1 会让项目失去"客观判断有没有变好"的唯一手段。若无法同时改造评测契约，**agent 化的收益将不可证伪**——这比收益不足更糟。
- **净结论**：支持**选择性 agent 化**（方案 ①→②，只读工具、有界步数、开关可关、评测契约同步改造）；反对整体 agent 化（方案 ③），尤其反对把写权限与自我升级交给模型。
- **优先级**：git 首提交 + 修 BUG-004 + 攒真实评测样本，**先于**任何 agent 化改造；否则在没有回滚点、没有真实数据、没有可信评测的状态下做架构重构，风险不可控。

### 决策点（需人工确认）

1. 目标定位：agent 化是**为提升对话质量**，还是**为减少人工操作**？（决定工具是否含写类）
2. 是否接受 **2~5× token 成本 / 3~10× P95 延迟** 换取动态诊断能力？

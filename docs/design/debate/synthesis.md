# 辩论综合结论（Synthesis）

- 决策主题：Socratic Tutor 技术栈与架构选型

- 日期：2026-09-02

- 模式：多代理辩论（3 架构师 + 当代言人 + 综合代理）

- 结论：**方案 B（Node/TS 单体 + 强 Provider 抽象 + 预留 Python sidecar 边界）**

***

## 1. 四维评分表

| 维度  | 方案 A（Python+FastAPI） | 方案 B（Node/TS）       | 方案 C（混合） |
| --- | -------------------- | ------------------- | -------- |
| 可行性 | 3（环境未确认）             | **5**（Node v24 已确认） | 2        |
| 风险  | 3                    | **4**               | 2        |
| 速度  | 3                    | **5**               | 2        |
| 质量  | 5                    | **4**               | 3        |

- 可行性/速度/质量：分越高越好。风险：分越高越安全。

## 2. 推荐结论

**采用方案 B：Node.js/TypeScript 单体后端 + 统一 Provider 抽象 + 轻量前端。**

理由：

- 唯一**已确认可用**运行时为 Node v24，零额外环境，最快跑通 Phase 1。

- Phase 1 为非实时语音，音频采集/回放压力在浏览器端，服务端仅转发，Node 无短板。

- TS 全栈共享类型，利于"苏格拉底引擎 + 画像/对话/反思 + 集成"这类编排重负载。

- 方案 C 系统性过重，排除；方案 A 生态优势真实但需未确认的 Python 环境，属后续红利，不必赌 Phase 1 开局。

## 3. 关键架构约束（方案 B 落地要点）

1. **强 Provider 抽象**：LLM / 向量 / ASR / TTS 全部定义为 TS interface + 工厂注册表，可挂本地/远程实现。默认豆包（Doubao），可切换。
2. **永久保留"AI 本地化边界"插件口**：

   - 优先 Node 原生绑定：`whisper-cpp-node`、`node-llama-cpp`（均有预编译二进制）。

   - 遇 Node 无好 SDK 的服务（SOTA 神经 TTS / 专用 ASR）：走 **sidecar Python 微服务**（进程外 HTTP/WS），Node 主进程仅经 Provider 接口调用，无代码侵入。撞墙时是"新增边界实现"而非重构。
3. **实时语音（Phase 2）解耦到 WebSocket 独立通道**，与文本链分离，升级不回归。
4. **非托管依赖标注**：FFmpeg 二次采样/音频格式用 `fluent-ffmpeg` 等标注官方替代，避免手写勘误。
